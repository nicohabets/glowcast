# Developer scripts

These scripts are tools for developing Glowcast; they are not part of the integration and HACS does not install them. They need the test requirements from `.github/workflows/ci.yml` (`pytest-homeassistant-custom-component` and `aiowebostv`), and `try_hue_output.py` and `try_pipeline.py` also need `hue-entertainment==0.1.2`.

- `try_webos_source.py`: runs the webOS frame source against a real LG TV and prints timings and average colours.
- `try_hue_output.py`: runs the Hue entertainment output against a real bridge: a left/centre/right pattern, a very dark colour, then stop.
- `try_pipeline.py`: runs the pipeline with the real TV source and Hue output for a while, then stops, and prints the start time, rates and stop reason.
- `try_ha_lights.py`: measures how fast lights follow Home Assistant's light actions (spike #125): colour updates at several rates, per light and as a group, without and with `transition`, through HA's websocket API (`GLOWCAST_HA_URL`, `GLOWCAST_HA_TOKEN`). It snapshots the lights first and restores them at the end, and prints a table per kind of light with generic labels. It only needs `aiohttp`.
- `render_brand.py`: builds the icon and logo PNGs in `custom_components/glowcast/brand/` from the sources in `docs/brand/`. It does not need the test requirements: run it with `uv run scripts/render_brand.py`, which installs its own pinned dependencies. See [docs/brand/README.md](../docs/brand/README.md).
- `render_hacs_readme.cjs`: renders `README.md` the way HACS shows it (the same `marked` and `xss` versions and settings), to check that no HTML shows as text. It needs Node and `npm install marked@15.0.4 xss@1.0.15`, not the test requirements; it is not part of CI.
- `check_links.py`: checks the links of the README and the built website (`mkdocs build -f website/mkdocs.yml` first): links to the site against the built site (with the `#anchor`), links to this repository's files on `main` against the working copy, and other links by fetching them (`--offline` skips those). It only needs the standard library; the `website` workflow runs it.
- The screen helper is not a script here but its own package in [`screen_helper/`](../screen_helper/README.md): it serves a computer's screen, or test patterns, to Glowcast. Start it from the repository root with `uv run --project screen_helper glowcast-screen` (`--pattern red` for a test pattern, without a screen); it does not need the test requirements.
- `demo.py`: a local Home Assistant with Glowcast from the working copy, to record GIFs of its flows and check the UI, and `demo.py room`, the illustrated room that shows what Glowcast sends to the lights; see below.
- `bench/run.py`: the test bench, Glowcast from the working copy against a real Hue light and a webcam; see the end of this page.

Dependency updates for the GitHub Actions, the screen helper (`screen_helper/uv.lock`) and the website (`website/requirements.txt`) come from Dependabot as weekly pull requests (`.github/dependabot.yml`); the test pins in `ci.yml`, which follow Home Assistant, and the demo's Home Assistant version are bumped by hand.

See the docstring at the top of each script for usage. Credentials come from environment variables; never put them in files in the repository.

## The local demo

`demo.py` runs Home Assistant 2026.10.4 (the "latest" version in `.github/workflows/ci.yml`; bump both together) on `127.0.0.1` with Glowcast from the working copy, a TV called "Living room TV" and a Hue bridge with the entertainment areas "TV area" and "Whole room". It does not need the test requirements; it installs its own.

- Nothing reaches a real TV or bridge: stub `hue` and `webostv` integrations (`demo/stubs/`) only report their entries as loaded, Glowcast syncs with a fake TV source and a fake light output (see below), the bridge is a fake one on `127.0.0.1` (`demo/fake_bridge.py`, including Hue's pairing reply), and Home Assistant loads no `default_config` and no discovery integration. `start` checks this for every instance and stops if it is not so. The stubs replace Home Assistant's own integrations: never copy them to a real Home Assistant.
- Switching Glowcast on keeps it syncing until it is switched off, so flows can record screens while it syncs. A third stub, `glowcast_demo` (`demo/stubs/glowcast_demo/`), replaces the `create` of the `webos` source and the `hue_entertainment` output in Glowcast's registries (`SOURCES`, `OUTPUTS`) with fakes: a TV source that is always on and returns a 64x36 picture of a few colours moving across it, made in memory, at about 4 captures per second (as the real TV); and a light output that accepts the colours and reports the area's channels with their positions (5 for "TV area", 3 for "Whole room", as the fake bridge lists them). Neither opens a network connection. The rest of the registry entries, the pipeline, the runtime, the entities and the status are Glowcast's own and run unchanged: the status is "streaming", the live settings apply without a restart, a new area restarts the pipeline, and switching off releases the fake lights. The log says "demo: fake TV source and fake light output active", and `start` checks that line. The stub also has a service, `glowcast_demo.discover_screen_helper`, that hands Glowcast a zeroconf discovery of a screen helper for the `screen-discovery` flow; nothing is looked for on the network. Like the other stubs, never copy it to a real Home Assistant.
- `start --no-fake-sync` starts without the `glowcast_demo` stub, with Glowcast's real TV source and light output, for example to check the "TV not reachable" path: no TV answers on `127.0.0.1`, so after the start-up grace (about 10 s) syncing stops with "the picture source is off or not reachable" in the log. The `entities` flow refuses to run on such an instance.
- Each working copy (each worktree) runs its own instance, so several sessions can use the demo at the same time. The instance is named after the working copy's folder and a short hash of its path (for example `glowcast-1a2b3c`); `--instance NAME` acts on another one. `start`, `record`, `stop` and `clean` act on their own instance only, and print its name. `record` refuses to run from another working copy than the one that started the instance.
- Ports: `start` picks them and stores them in the instance's `state.json`; `record` and `status` read them from there. The first instance gets `8199` (Home Assistant) and `8443` (the fake bridge) when they are free, the others get the next free ones from there up: look up the URL with `status` or in `start`'s output.
- Everything it makes lives in `~/.cache/glowcast-demo`, outside the repository (except the output of `room`, below): per instance the config directory, pid files, logs, GIFs and screenshots in `instances/<instance>/`, and one virtual environment for all of them in `venv/`. Playwright keeps its Chromium in `~/.cache/ms-playwright`. `start` and `clean --all` take a lock (`~/.cache/glowcast-demo.lock`), so two of them never install, pick ports or remove things at once; the environment is only changed (a pin bumped here) while no instance runs, and Home Assistant runs with `--skip-pip`, so a running instance never installs into it. A requirement added to Glowcast's manifest must be added to `REQUIREMENTS` in `demo.py` too.
- A demo from before instances (state directly in `~/.cache/glowcast-demo/config` and `run/`) shows as the `legacy` instance in `status`; `stop --instance legacy` stops it and `clean --instance legacy` removes its config, logs and recordings. While it exists, new instances leave `8199` and `8443` to it. A session still on the old `demo.py` removes all of `~/.cache/glowcast-demo` with its `clean`, other instances included.
- `ffmpeg` for the GIFs comes with the `imageio-ffmpeg` package in the demo's environment; no system install needed.
- It runs with Python alone on Linux and macOS (on Windows in WSL). Home Assistant needs Python 3.14.2 or newer; if the Python you run `demo.py` with is older, it uses [uv](https://docs.astral.sh/uv/) to fetch one.

```
python3 scripts/demo.py start                          # first run installs (a few minutes)
python3 scripts/demo.py start --no-fake-sync           # Glowcast's real TV source and light output: syncing stops after about 10 s
python3 scripts/demo.py record                         # every flow; or name some: setup settings device entities screen-setup screen-discovery
python3 scripts/demo.py record --lang nl --theme dark  # en|nl, light|dark; --out DIR
python3 scripts/demo.py record settings --still        # a PNG of each step instead of a GIF
python3 scripts/demo.py stop
python3 scripts/demo.py clean                          # stop and remove this instance
python3 scripts/demo.py status                         # all instances: working copy, ports, running, URL
python3 scripts/demo.py stop --instance legacy         # --instance NAME: another instance
python3 scripts/demo.py clean --all                    # stop all and remove ~/.cache/glowcast-demo (asks first; --yes)
```

`start` always begins with a fresh config directory without a Glowcast entry. Log in at the URL `start` prints (http://127.0.0.1:8199 for the first instance) as `demo` / `demo-password` to look around.

`record` sets Home Assistant's own language to `--lang` too (entity names come from the server in its language, not from the profile), and records in Home Assistant's mobile view (400 px wide at device scale factor 2, so 800 px wide with sharp text), with a ring where each click lands and a short pause on each step, and saves one GIF per flow as `<lang>-<theme>-<flow>.gif` in the instance's `recordings` folder (it warns when one is over GitHub's 10 MB). The flows:
- `setup`: the setup flow from "Do you want to set up Glowcast?": the menu (LG webOS TV), TV, bridge, link button, pairing (the fake bridge answers), area, done. It first removes a Glowcast entry from an earlier run.
- `settings`: from the integration page to the settings screen, choosing another update rate, saving.
- `device`: from the integration page to Glowcast's device page.
- `entities`: on the device page, switching Glowcast on, then changing the settings under Configuration while it syncs: brightness, intensity, update rate and entertainment area (#13; the new area restarts the pipeline, the switch stays on), and switching off. It starts switched off, from the default settings, and waits until the pipeline streams (read from the diagnostics).
- `screen-setup`: a computer screen set up by hand (#109): the menu (Computer screen), the helper's address and port, the pairing code, up to the Hue bridge step (the output's steps are the same as for a TV; the flow is aborted after the recording). It starts the screen helper itself (`uv run --project screen_helper glowcast-screen --pattern cycle --name "Test PC" --host 127.0.0.1 --non-interactive --pairing-code 123456`, on port 8488 if free, with its own config directory in a temporary folder, so the computer's own helper id and pairings are never touched; on 127.0.0.1 it does not announce itself). It first removes the Glowcast entries from an earlier run.
- `screen-discovery`: the same helper as discovered by Home Assistant (#109): the card "Glowcast - Test PC" under Discovered, Add, a wrong pairing code and its error, the right code, then the output's steps, ending on the new device's page. The demo loads no zeroconf integration, so the flow hands Glowcast the discovery itself through the `glowcast_demo` stub's service `glowcast_demo.discover_screen_helper` (host, port, id, name), as Home Assistant's zeroconf integration would; it needs the stub, so not with `--no-fake-sync`.

The other flows set Glowcast up first (unrecorded) if needed. With `--still`, each step is saved as `<lang>-<theme>-<flow>-<nn>-<name>.png` instead, in the same mobile view. If a flow fails, `error.png` shows the page at that moment. GIFs and screenshots for a pull request go up as GitHub attachments (rule 11 in `CLAUDE.md`); do not commit them.

To add a flow (for example new entities or a status), write a function in `demo/record.py` that takes a `Recorder`: open the first screen (`rec.goto(...)`), call `rec.begin()` when it is ready (the GIF starts there), click with `rec.click(...)` and call `rec.step("name")` on each screen worth a pause; then add it to `FLOWS` there (`demo.py` passes flow names on). Find buttons by slot, by option value (`rec.option(...)`) or by the frontend's own texts (`rec.localize(...)`), not by English labels, so the flow works in both languages.

## The end-to-end run: test patterns in, colours at the bridge

`demo.py e2e` checks the whole chain without a TV, a screen or lights (#112): the screen helper's test patterns go through Glowcast's real screen source, pipeline, colour engine and Hue entertainment output, and the demo's fake bridge checks the colours it receives. Run it before opening a pull request that touches a source, the pipeline, the colour engine or an output; CI runs it too (the `end-to-end (test patterns)` job, about 3 minutes with the install).

```
python3 scripts/demo.py e2e           # about 2 minutes once the demo's environment is installed
python3 scripts/demo.py e2e --keep    # leave Home Assistant and the fake bridge running afterwards
```

- It runs on an instance of its own, `<this working copy's instance>-e2e`, with its own ports, so it never touches the instance you record with. It needs `uv` (for the screen helper) and the demo's environment (installed on the first run, as for `start`), and it starts a fresh config directory every time. Without `--keep` it stops everything at the end, also after a failure. The instance's folder stays (logs and summary) until you remove it with `python3 scripts/demo.py clean --instance <name>-e2e` (`status` shows the name) or `clean --all`. It does not install Playwright's Chromium (only `start` does, for `record`).
- The same isolation as the demo, checked at the start: everything listens on `127.0.0.1` only, no discovery integration is loaded, and the screen helper runs with `--host 127.0.0.1`, so it does not announce itself. Instead of `glowcast_demo`, a stub `glowcast_e2e` (`demo/stubs/glowcast_e2e/`) is loaded: Glowcast keeps its own source and output.
- The fake bridge (`demo/fake_bridge.py`) answers the Hue output's REST calls (`/auth/v1`, the areas with their streaming status, `action: start` and `stop`) and, with `--dtls-port`, runs the stream's side: a minimal DTLS 1.2 server with a pre-shared key (just what `hue-entertainment`'s client does: `TLS_PSK_WITH_AES_128_GCM_SHA256`, the app key as identity, the client key as key) on UDP `127.0.0.1`. It decrypts every HueStream message; a record only decrypts with the right key. It writes every request, claim, handshake and colour message as a JSON line to `run/bridge/events.jsonl` in the instance's folder.
- One thing is redirected: `hue-entertainment` always streams to UDP port 2100 on the bridge's host, and the demo's bridge is `127.0.0.1:<port>`. The `glowcast_e2e` stub changes only that address, to the fake bridge's DTLS port on `127.0.0.1`, and refuses any other host. The library's REST calls, handshake, encryption and messages, and Glowcast's whole Hue output, run unchanged.
- `demo/e2e.py` does the steps: it starts the helper (`--pattern cycle`, each pattern for `NO_PICTURE_WAIT` from `core/pipeline.py` plus 3 s, the name "Test PC", pairing code `123456`, its own config directory), sets Glowcast up through the real setup flow over Home Assistant's REST API (Computer screen by hand, the helper's address and pairing code, the bridge, the link button, the "TV area"), switches it on, and checks one full cycle of patterns from the first `red` whose settled part (below) falls while it streams. For each pattern it compares every message in the settled part of the pattern (from 2 s after it starts) with the expected colours at the default brightness of 80 % (204 of 255): `red`, `green`, `blue` and `white` on all channels; `left-red-right-blue` red on the left channels and blue on the right ones (the middle one sees both and is left out); `letterbox` green on all channels, also the one at the top centre, whose region includes the black bar. `black` is all zero, so Glowcast takes it as no picture (#68): the colours of `white` hold, after `NO_PICTURE_WAIT` (read from `core/pipeline.py`, so a change there needs no change here) the bridge gets `action: stop` and the stream stops, the status shows `no_picture`, and the next pattern claims the area again. Then: every record decrypted, every handshake with the right key, messages only for the claimed area, and exactly one new claim after `black`. Whether Glowcast sends 8-bit values is not checked here: `hue-entertainment` writes an 8-bit value twice and shifts a 16-bit one down, so the wire looks the same; the unit tests cover that rule. And: stopping the helper turns the switch off with `tv_off` and releases the lights; `--unpair` and a restart of the helper make the next switch-on stop with `source_auth_failed` and start a reauth flow; pairing again in that flow syncs again, and switching off releases the lights.
- Output: `PASS` or `FAIL` with details per step, then a JSON summary (also in `e2e-summary.json` in the instance's folder): `passed`, each step with `passed` (`null` when skipped after a failed step it needs), its details, and the status sensor's changes over the run. The exit code is 1 if a step failed. The helper's events are in `e2e/helper.log`, Home Assistant's log in `config/home-assistant.log`; in CI they are uploaded as the `e2e-logs` artifact when the job fails.

## The room: what Glowcast sends to the lights

`demo.py room` draws what Glowcast sends to the lights in the illustrated living room of the README (the one in `docs/images/illustrations/`), for a fixed set of pictures. It is for reviewing pull requests (rule 11 in `CLAUDE.md`): it shows a change to the colours, the timing or the stopping before anyone tests it on real hardware. It needs no Home Assistant instance, TV, bridge or lights, and it does not need `start`; it uses the demo's environment (with `resvg-py` to draw). The first run after `resvg-py` was added installs it, which `demo.py` only does while no demo instance runs: stop them first if it asks.

```
python3 scripts/demo.py room             # this working copy
python3 scripts/demo.py room --compare   # the merge base with main and this working copy, side by side
```

- `demo/room_harness.py` runs six scenario pictures (64x36, made in code) through `core/`'s own pipeline, colour engine and light state, on a fake clock stepped per send tick (25 per second), with a scenario TV source and a recording light output: 1 sunset, 2 a sudden dark picture (the lights hold for `BLACK_HOLD`, then fade to the glow), 3 a saturated red, 4 a letterbox picture, 5 a fade from one scene to another, 6 no picture (all-zero frames: the lights are released after `NO_PICTURE_WAIT` and drawn off). The timings come from `core/`. Two runs give the same colours.
- The recording output has seven channels, one per light in the room: the strip's left side, three along its top and its right side, the floor lamp (left, low) and the light bar (right, low). The layout and what each channel stands for are in `CHANNELS` in `demo/room_harness.py`; a new kind of light (loose lights, #76) gets a row there and a drawing in `demo/room.py`.
- `demo/room.py` draws each sample: the TV shows the picture Glowcast got, scaled up without smoothing; each light shows the colour of its channel at full brightness, its glow as strong as the brightness Glowcast sent (with a display gamma, so the dim glow stays visible). A light that is released or never claimed is drawn off.
- `--compare` fetches `main` (`git fetch origin +refs/heads/main:refs/remotes/origin/main`), adds a temporary worktree at `git merge-base HEAD origin/main`, runs the same harness against that commit's `core/` and removes the worktree again, also after an error or Ctrl+C. The rooms are labelled "main" and "this PR" (this working copy, uncommitted changes included). If main's `core/` cannot run the scenarios, or `main` cannot be fetched (offline, no `origin`), it says so and draws this side only.
- Output, in `room-out/` (ignored by git; `--out DIR` for another folder): `room.gif` with all scenarios (800 px per room, 1600 px side by side, 12.5 frames per second, fewer only if it would be over 10 MB), and per scenario `room-<n>.gif` and a still `room-<n>.png`. The GIFs have a light background (a GIF with a transparent one is five times the size); the stills are transparent around the room, like the illustrations. Attach them to the pull request with `gh pr comment <n> --attach ...`; never commit them.

## The test bench

`bench/run.py` (#134) checks Glowcast on real hardware without the TV: a computer monitor gives the picture, one or more Hue lights in the bench's own entertainment area follow it, and a USB webcam that sees both judges the colours and the timing. When an agent runs it is in `CLAUDE.md` ("Working in parallel", rule 6).

```
python3 scripts/bench/run.py --suite basic --mode both      # both modes, about 10 minutes
python3 scripts/bench/run.py --suite extended --mode screen # also settings and diagnostics
python3 scripts/bench/run.py --dry-run                      # print the steps, touch nothing
python3 scripts/bench/run.py snapshot                       # one camera frame with the regions drawn
python3 scripts/bench/run.py pair-bridge --host 192.0.2.10  # once: the bench's own Hue key (link button)
```

Options: `--mode pattern|screen|both` (default both), `--suite basic|extended` (default basic), `--keep-images` (keep camera frames from before and after the run, in the report folder), `--wait SECONDS` (wait for another run's lock instead of skipping), `--config FILE`.

**What it needs.** A Windows computer with WSL2 in mirrored networking mode (the Hue stream leaves WSL2 that way, see "Verified facts"); [uv](https://docs.astral.sh/uv/) on Windows (`winget install astral-sh.uv`, found with `where.exe uv`); a second monitor; a USB webcam that sees that monitor and the bench lights; an entertainment area of the bench's own on the bridge, with "When syncing stops: Last on-state" in the Hue app (with "Pause on the last colour" the lights keep the last colour, #142); and a Hue key of the bench's own (its own application id; never the key of the Glowcast that runs the TV). Make that key once with `run.py pair-bridge --host <the bridge's address>`: press the bridge's link button within 30 s, and it writes `{"host", "app_key", "client_key"}` with mode 600 to the config's `bridge_keys` file, printing nothing secret. It never replaces an existing key file without `--force`; an old key stays on the bridge until you remove it in the Hue app. The script runs in WSL and starts the Windows parts itself with Windows' `uv.exe`: `bench/win/camera.py` (OpenCV with DirectShow, the settings of spike #133), `bench/win/screen.py` (a borderless full-screen Tk window) and the screen helper, all on `127.0.0.1`.

**The configuration** is local and never committed: copy `bench/config.example.yaml` to `bench/config.local.yaml` (ignored) or to `~/.config/glowcast-bench/config.local.yaml` (shared by all working copies; the first one wins), and fill it in. The regions in it are a starting point and their sizes: every run finds the lights and the monitor itself (below) and reports how far they moved. Check them on a `snapshot` (saved in `~/.cache/glowcast-bench/snapshots/`; delete it afterwards and never attach it): a region per light on what it lights (a wall), or on a spot including its rim; never on the wall right behind the monitor; and one on the monitor, for the delay in screen mode.

**What a run does.**
- It takes a lock (`~/.cache/glowcast-bench/bench.lock`: one bench for all working copies). A second run skips with exit code 4, or waits with `--wait`.
- It reads the bridge (GET only, with the bench's key). If an area other than the TV's or the bench's streams, it stops with "skipped: the bridge is streaming another area" (exit code 3) and touches nothing. If the TV's area streams with the bench's own key, it stops with a configuration error (exit code 2): the bench needs a key of its own. If the TV's Glowcast streams the TV's area, it switches that Glowcast off through the product owner's Home Assistant and back on at the end (also after Ctrl+C or a failure), and the report says for how long. If another app streams the TV's area, it skips (exit code 5).
- It notes the bench lights' state (Home Assistant and the bridge).
- **Every run starts with a calibration** (unattended, no snapshot needed); a failure stops the run with exit code 7:
  - **The picture before the run:** before anything is touched, the camera keeps the lights' picture at the configured exposure.
  - **Camera position:** all lights off, then each light alone at full brightness in warm white and off again; the camera worker finds the window of the configured size that brightens most for that light, against both pictures without it (so something else that changed meanwhile does not count) and not for the other lights (`bench/win/locate.py`). The monitor is found the same way by flashing the full-screen window white (also in pattern mode, when the config has a `monitor`; without one, the report says the monitor region was not located). The found regions are used; the report gives each one, how far it moved (a warning above 40 px for a light) and how far it stands above the picture's median change. A light or the monitor that changes too little or stands out too little (camera moved or blocked), or two regions on top of each other, fail the calibration.
  - **Left and right** come from the bridge. While a light is on alone, the bridge says which of the area's lights is on, so each light in Home Assistant is matched to a bridge light and its camera region; that light's x in the area is its channels' x (their mean for a gradient strip). With the x positions apart, `left-red-right-blue` expects red on the left light and blue on the right one; the report gives the mapping. When the channels sit apart but a light cannot be matched (no bridge light or two came on), the calibration fails rather than skipping the step quietly.
  - **Exposure:** with the lights in warm white at full brightness and then off, the exposure steps from -11 to -5. Every light region must stand well above dark, and one that clips at some exposures must have its 95th percentile under 240. A region that clips at every exposure (a spot's core) is judged on its rim: at most 70 % of its pixels may clip (59 % at -8 on this bench). The run uses the brightest exposure that fits (the darkest when only such clipping regions are there). White balance stays fixed at the configured temperature.
  - **References and ambient light:** at that exposure, the white (warm), cool and dark (lights off) references. The dark reference is the ambient light: more than 35 % of the white level (daylight through a window) fails the calibration ("too much ambient light"), as colours would not be reliable.
  - **Back to the state before the run:** the lights are set back, and the camera checks them at the configured exposure against the picture from before the run ("the lights did not come back to their state before the run" fails the calibration). Their picture at the chosen exposure is then the reference for every restore in the run, so the restores prove the real state before the run.
- It starts a local Home Assistant for this working copy, like the demo (the demo's environment and stubs, in `~/.cache/glowcast-bench/instances/`, from port 8299), with Glowcast from the working copy: the screen source on the helper at `127.0.0.1`, and the real Hue output on the bench area with the bench's key. Unlike the demo, it reaches the real bridge.
- **Pattern mode:** the helper serves `--pattern cycle` (red, green, blue, white, black, left-red-right-blue, letterbox) for two cycles, each pattern the no-picture wait plus 5 s (at least 8 s). The bench takes its timing from Glowcast's own constants (`NO_PICTURE_WAIT` in `core/pipeline.py`, `BLACK_HOLD` in `core/light_state.py`; `Timing` in `bench/report.py`), so a change of either needs no change in the bench. Checked: the area streams after switch-on; each colour on each light; black, which is all zero, holds the colours for the hold on black (and shows the glow when the no-picture wait is longer, as with 7 s), then releases the lights after the wait for "no picture" (#68) and the camera sees them back in their pre-run picture; the next picture claims them again; the delay per colour change, from the helper's change to the light passing halfway in the camera. That delay includes the camera's own latency (up to about 75 ms, #133), since only the light is seen.
- **Screen mode:** the full-screen window on the monitor, captured by the helper (`--screen`, found by the monitor's position). First a self-check: the helper's frame is the window's red, and near-black (`#101010`) is not all zero. Checked: the colours; a near-black shorter than the hold on black holds them; a longer one holds them for the hold, then shows the warm glow while the area keeps streaming; the delay from the monitor changing to the light changing, both in the same camera frames, so the camera's own latency cancels out. A change the camera does not see on the monitor is timed by the window instead; the report counts those ("changes timed by the window").
- In both modes: switching off releases the area and the lights come back (the camera decides; the bridge's state is reported as a second opinion, but it is no proof, #142); switched on again, stopping the helper stops Glowcast with `tv_off` and the lights come back. `left-red-right-blue` is skipped when the lights' channels sit at the same x on the bridge.
- `--suite extended` adds: the diagnostics contain none of the run's keys, addresses, ids or names; in screen mode, red and blue stay pure at brightness 20 % and 80 % on the lights marked `pure: true` (no warm white mixed in, #43; the brightness is set back to 80 % afterwards); brightness, intensity and update rate changed while syncing take effect without a new handshake (the area stays active with one streamer, the status never "starting"); a brightness changed while off is stored and Glowcast stays off. "No picture through a locked screen" is reported as skipped: an unattended run cannot unlock the computer.
- At the end, on every exit path (Ctrl+C included), in this order: the bench Glowcast off and its area inactive (if the area keeps streaming, the local Home Assistant is stopped, and the step fails if even that does not help); the lights set back explicitly to their pre-run state through Home Assistant and checked with the camera; the TV's Glowcast switched back on if the run switched it off, and read back (a failed step, and a message in the terminal, if it is not on); then the helper, the window, the camera and the local Home Assistant stopped. The bench only stops processes it started itself: a helper port that is already taken stops the run (exit code 6).

**The report** goes to `~/.cache/glowcast-bench/reports/<time>/`: `report.md` and `report.json` (pass, fail or skip per step, with timings, numbers and fixed texts only, so it can be attached to a public pull request; the lights are called "light 1", "light 2" and so on, never by their names in the config, and details of an error go to the terminal only; the format is meant for the TV's check, #71, too) and `raw.json` (the camera means and the events, to tune the tolerances; keep it local). Images only with `--keep-images`, in `images/` there. The tolerances are `Thresholds` in `bench/report.py` (overridable under `thresholds:` in the config); `tests/test_bench_report.py` and `tests/test_bench_calibration.py` check that logic and the calibration's on recorded numbers in CI, and `tests/test_bench_local_ha.py` checks that the parts of `demo.py` the bench builds on are still there. The run itself needs the hardware and is not part of CI.

Exit codes: 0 passed, 1 a step failed (or Ctrl+C), 2 a usage or configuration error (checked before anything is touched), 3 skipped: another area streams, 4 skipped: another bench run, 5 skipped: another app streams the TV's area, 6 the bench itself could not finish (for example the camera or the local Home Assistant did not start), 7 the calibration failed (a light or the monitor not found, no usable exposure, too much ambient light).

Through the product owner's Home Assistant the bench only calls `light.turn_on`/`light.turn_off` on the configured lights and `switch.turn_on`/`switch.turn_off` on the configured TV switch (`bench/clients.py` refuses anything else), and it only sends GET requests to the bridge.
